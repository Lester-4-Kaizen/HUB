Part 1 — The Evolution of AI

The reference document grounds everything in the three-phase evolution of AI systems — each phase building on the last, requiring new architectural approaches as AI becomes more autonomous.

Phase 1 — Predictive AI

Traditional machine learning systems trained on historical data to predict future outcomes. These systems operate within fixed problem scopes: classify this image, predict this price, detect this fraud. They are reactive and narrowly scoped — they answer specific questions with statistical models. Examples: fraud detection models, recommendation engines, demand forecasting pipelines.

Key characteristic: given input X, produce output Y. The model does not plan, reason across steps, or take actions in the world. It simply maps inputs to outputs based on learned patterns.

Phase 2 — Generative AI

Foundation models (LLMs, diffusion models) that generate novel content — text, images, code, audio. Examples: ChatGPT, DALL·E, Stable Diffusion, GitHub Copilot. Generative AI expanded AI's role from prediction to creation, but still required human orchestration for complex multi-step tasks.

Key characteristic: given a prompt, produce creative or informative content. The human remained in the loop to decompose goals, connect results, and decide next steps.

Phase 3 — Agentic AI

Autonomous systems that plan, reason, act, and self-correct to achieve goals over time. Unlike Generative AI (which responds to prompts), Agentic AI can:

  • Break complex goals into sequences of sub-tasks
  • Invoke external tools — APIs, databases, code interpreters, web search
  • Maintain memory and context across multiple interactions
  • Evaluate outcomes and revise plans when things go wrong
  • Coordinate with other agents to divide and conquer large tasks
The Core Shift: Predictive AI classifies. Generative AI creates. Agentic AI acts. This transition from reactive to proactive systems is what makes Event-Driven Architecture essential — agents need infrastructure that supports asynchronous, coordinated, long-running workflows.

Part 2 — Anatomy of an AI Agent

An AI agent is not a single component — it is a system of interacting parts that together enable autonomous, goal-directed behavior. Understanding the anatomy helps you design agents that are reliable, extensible, and observable.

Core Components

🧠 LLM / Reasoning Core
The cognitive engine. Processes context, formulates plans, decides which tool to call next, and generates responses. Typically a large language model (GPT-4, Claude, Gemini, Llama).
💾 Short-Term Memory
The active context window — everything the agent currently "remembers" about the current task: prior messages, tool results, partial plans. Limited by the LLM's context length.
🗄️ Long-Term Memory
Persistent storage that survives across sessions. Usually a vector database (Pinecone, Chroma, Weaviate) that stores past experiences, domain knowledge, and user preferences — retrieved by semantic similarity.
🔧 Tools / Actions
The agent's hands. External capabilities it can invoke: web search, code execution, database queries, API calls, file I/O, email sending. Each tool has a defined interface the LLM can call.
📋 Planner
Decomposes high-level goals into a sequence of concrete, executable steps. Approaches: ReAct (interleave reasoning with action), Chain-of-Thought, Tree-of-Thought, Plan-and-Execute.
🔄 Feedback / Evaluator
Observes the results of each action, compares against the goal, and decides whether to continue the current plan or re-plan. Enables self-correction — a defining capability of robust agents.
📡 Communication Interface
How the agent receives tasks and reports results. In EDA systems this is the event bus — the agent consumes task events and publishes result events. In simpler systems it may be a REST API or message queue.
🆔 Identity / Profile
The agent's defined role, capabilities, and constraints. In multi-agent systems, each agent has a declared identity so the orchestrator knows what tasks to assign to it.

The ReAct Agent Loop

The most widely used agent pattern is ReAct (Reason + Act) — the agent alternates between reasoning steps and tool invocations:

Goal received → Thought: "What is the first step I need to take?" → Action: call_tool("web_search", query="...") → Observation: search results returned → Thought: "Based on results, I need to..." → Action: call_tool("code_executor", code="...") → Observation: code output → Thought: "Goal achieved / need to revise plan because..." → Final Answer: deliver result

This loop continues until the agent determines the goal is satisfied or a maximum iteration limit is reached. The key insight is that reasoning and action are interleaved — the agent can observe results before deciding its next move.

Memory Architecture in Detail

Agent memory operates at multiple timescales:

  • In-context (working memory): Everything in the current LLM prompt — limited by context window (e.g., 128K tokens for GPT-4o). Very fast access, but ephemeral.
  • External short-term (episodic): Recent task history stored in a database, retrieved for the current session. Survives context window limits.
  • External long-term (semantic): Accumulated knowledge, user preferences, domain facts. Stored as vector embeddings in a vector DB. Retrieved by similarity to current query.
  • Procedural: The agent's "how-to" knowledge — often encoded in system prompts or fine-tuning rather than explicit retrieval.

Part 3 — Event-Driven Architecture (EDA)

Event-Driven Architecture is a software design paradigm in which system components communicate by producing and consuming events — discrete, immutable records that something notable has happened — rather than via direct synchronous API calls.

Core Vocabulary

📨 Event
An immutable record: "Payment of $150 processed at 14:32:01". Contains: event type, timestamp, source, payload, and optionally a correlation ID for tracing related events.
📢 Producer (Publisher)
A component that emits events when something happens. Producers are decoupled — they don't know which consumers (if any) will react to their events.
📥 Consumer (Subscriber)
A component that subscribes to specific event types and reacts when they arrive. Multiple consumers can independently react to the same event — no coordination required.
🚌 Event Bus / Broker
The messaging infrastructure routing events from producers to consumers. Examples: Apache Kafka, AWS EventBridge, Google Pub/Sub, RabbitMQ, NATS.
📊 Event Stream
A persistent, ordered, append-only log of events. Unlike traditional message queues (messages deleted after consumption), streams retain events — enabling replay, auditing, and time-travel debugging.
📁 Topic / Channel
A named category of events. Producers write to topics; consumers subscribe to topics. Example topics: "agent.tasks", "agent.results", "agent.errors", "payment.processed".

Why EDA is the Right Architecture for AI Agents

Traditional request-response (REST APIs) works well for simple, fast, synchronous interactions. But AI agents — especially multi-agent systems — have characteristics that make REST a poor fit:

Agent Requirement Problem with REST EDA Solution
LLM inference is slow (seconds to minutes) Caller must wait, holding a connection open Fire-and-forget event; caller gets result via event when ready
Multiple agents need shared context Each pair needs its own API contract Shared event stream acts as common "working memory"
Scale agent instances up/down independently Tight coupling makes independent scaling hard Producers/consumers scale independently based on queue depth
Full audit trail of decisions REST logs don't capture causality chains Event log captures every action, input, and output in sequence
Fault tolerance — agents can crash In-progress request is lost if agent restarts Events are persisted; agent resumes from last committed offset
Fan-out — one task triggers many agents Caller must manage multiple parallel calls One event can be consumed by N agents independently

Part 4 — EDA Design Patterns for Multi-Agent Systems

The document covers four foundational patterns for coordinating multiple AI agents. Each pattern makes different tradeoffs between control, flexibility, fault tolerance, and complexity.

🎯 Pattern 1: Orchestrator-Worker
Centralized Control

A central Orchestrator agent receives the top-level goal, decomposes it into sub-tasks, assigns each sub-task to a Worker agent via an event, and aggregates the results into a final output.

Event flow:

User Goal Event → Orchestrator → Task Events (one per worker) → Workers process → Result Events → Orchestrator → Final Output Event

When to use: Structured, predictable workflows where the task decomposition is well understood. Examples: document processing pipeline (parse → extract → summarize → format), code review (lint → test → security scan → review), customer query routing.

Strengths: Simple to reason about; clear chain of responsibility; workers are stateless and horizontally scalable; easy to add new worker types.

Weaknesses: Orchestrator is a single point of failure; bottleneck if the orchestrator is slow; poor fit for tasks where the decomposition is unknown upfront.

🌳 Pattern 2: Hierarchical Multi-Agent
Multi-Level Coordination

A tree of agents: a Top-Level Manager decomposes the goal and routes sub-goals to Department Managers, each of which further decomposes and routes to Worker agents. Each level communicates through its own event channels.

When to use: Large-scale enterprise systems where different sub-domains have their own expertise and policies. Example: a company-wide AI assistant where a top-level agent routes to HR, Finance, Engineering, and Legal sub-agents, each of which has their own specialist workers.

Strengths: Scales to very large systems; clear separation of concerns; sub-hierarchies can be developed and deployed independently.

Weaknesses: High design complexity; deep call chains increase latency; debugging requires tracing across multiple levels.

📋 Pattern 3: Blackboard (Shared Knowledge)
Collaborative / Emergent

All agents share access to a common event stream — the "blackboard". Any agent can publish observations, partial results, or hypotheses. Any agent can consume others' contributions and build on them. There is no single coordinator — the solution emerges from collective contributions.

When to use: Problems where no single agent has complete knowledge and the best solution emerges iteratively. Examples: scientific hypothesis generation, collaborative document drafting, complex debugging where different specialist agents surface different insights.

Strengths: Highly flexible; enables emergent behavior; no single point of failure; specialists contribute at their own pace.

Weaknesses: Hard to reason about; can produce conflicts if agents publish contradicting information; requires careful event schema design; harder to guarantee task completion.

[IMAGE — Figure 6] Insert image here — Blackboard pattern diagram: multiple specialized agents all reading from and writing to a shared central event stream
💰 Pattern 4: Market-Based (Competitive Bidding)
Self-Organizing

Tasks are published as events on an open market. Specialist agents bid for tasks based on their current capabilities, load, and confidence. A Task Allocator evaluates bids and assigns the task to the most suitable bidder, who then executes and reports results.

When to use: Dynamic workloads where the right agent depends on current conditions (load, expertise, availability). Examples: cloud resource allocation, distributed rendering pipelines, content moderation at scale, logistics optimization.

Strengths: Self-organizing; resilient (if one agent is overloaded, another wins the bid); naturally load-balances; encourages agent specialization.

Weaknesses: Bidding overhead adds latency; requires agents to accurately self-assess capabilities; more complex to implement and debug than Orchestrator-Worker.

Part 5 — Apache Kafka for Agent Coordination

The document uses Apache Kafka (Confluent's core product) as the reference event streaming platform. Kafka is the de facto standard for high-throughput, fault-tolerant event streaming in production AI systems.

Key Kafka Concepts

📁 Topic
Named, partitioned event channel. Agents subscribe to relevant topics. Example: "tasks.research", "results.research", "errors.all".
📦 Partition
Topics split into N partitions. Each partition is an ordered log. Multiple agent instances consume different partitions in parallel — enabling horizontal scale.
🔖 Offset
Position of an event within a partition. Consumers track their offset — if a consumer crashes, it resumes from the last committed offset. No work is lost.
👥 Consumer Group
N agent instances in the same group collectively consume a topic. Kafka distributes partitions evenly — natural load balancing without any orchestration code.
🔄 Exactly-Once
Kafka's strongest delivery guarantee. Each event processed exactly once even across failures. Critical for financial agents, medical agents — duplicate actions could be catastrophic.
⏳ Retention Policy
Events stored for configurable duration (minutes to forever). Full retention enables event replay — debugging agent misbehavior by replaying the exact same event sequence.

Sample Agent Event Structure

{ "event_id": "evt_9a2f1b3c", "event_type": "TASK_ASSIGNED", "schema_version": "1.0", "timestamp": "2025-03-15T09:41:22.341Z", "source_agent": "orchestrator-prod-01", "target_agent": "research-worker", "correlation_id": "goal_xyz789", // ties all events for one goal together "payload": { "task_id": "task_042", "task_type": "web_research", "query": "recent advances in agentic AI 2025", "deadline": "2025-03-15T09:42:22Z", "priority": "HIGH", "context": "Part of user goal: write a research summary" } }

Designing Agent Topics

Well-designed topic schemas are critical for maintainable multi-agent systems. Recommended topic naming convention:

  • agent.{agent-type}.tasks — incoming task assignments
  • agent.{agent-type}.results — completed task outputs
  • agent.{agent-type}.errors — failed tasks with error details
  • agent.{agent-type}.status — heartbeat / health events
  • workflow.{workflow-id}.events — all events for a specific goal (for tracing)

Part 6 — Building Agentic Projects: Practical Guide

This section synthesizes the practical recommendations from the reference for implementing your own agent systems.

Step 1 — Define Scope and Goal

Before writing any code, clearly define: What is the agent's objective? What are the success criteria? What tools/APIs does it need? What data sources will it use? What's the failure mode if it gets stuck?

Step 2 — Choose the Right Pattern

Map your problem to one of the four patterns. Start with Orchestrator-Worker unless you have a strong reason for another — it's the easiest to implement, test, and debug. Add complexity only when the simpler pattern genuinely can't handle your use case.

Step 3 — Design Your Event Schema First

Define all events before writing any agent code. For each event specify: event_type, required fields, optional fields, and which agents produce/consume it. Treat this like a contract — changing event schemas in production is painful.

Step 4 — Implement the Core Agent Loop

class Agent: def run(self): while True: # 1. Observe — get next task event event = self.event_bus.consume(self.task_topic) # 2. Recall — retrieve relevant memory context = self.memory.search(event.correlation_id) history = self.memory.get_recent(event.correlation_id) # 3. Plan — reason about what to do next plan = self.llm.plan( goal=event.payload, context=context, history=history, available_tools=self.tools.list() ) # 4. Act — execute the next action result = self.tools.execute(plan.next_action) # 5. Store — save what happened self.memory.store(event.correlation_id, result) # 6. Emit — publish result or next task if plan.is_complete: self.event_bus.publish(self.result_topic, result) else: self.event_bus.publish(self.task_topic, plan.next_task)

Step 5 — Add Memory Incrementally

  • Start: Pass last N tool results in the LLM context window
  • Add: A simple key-value store (Redis) for session state
  • Scale: A vector database (Chroma, Pinecone) for semantic retrieval across sessions

Step 6 — Observability from Day One

Instrument every agent action. You should be able to answer: "Why did the agent take action X at time T?" The event log is your primary debugging tool — keep it complete and searchable. Add span tracing (OpenTelemetry) to correlate events across agents using the correlation_id field.

For Your Finals Agentic Projects: Start with the Orchestrator-Worker pattern on a simple task you understand well. Use a lightweight message queue (Redis Streams or even a simple in-memory queue) before committing to Kafka. Define clear event schemas. Build the feedback/evaluator loop early — it's what separates a fragile demo from a robust agent.

Part 7 — Real-World Applications

Customer Support Automation

Customer message arrives as an event → Classifier agent routes to specialist (billing, technical, returns) → Specialist researches and drafts a response → Quality agent reviews → Response delivered. EDA allows each step to run asynchronously — customers don't wait while backend agents work in parallel.

Software Development Pipeline

Code commit event → Lint agent → Test runner agent → Security scanner agent → Code review agent → Deploy agent. Failures at any stage emit an error event that triggers a remediation agent. The entire pipeline is observable through the event log.

Healthcare Diagnostics

Patient data event → Imaging analysis agent + Lab results agent + Medical history agent (parallel, Blackboard pattern) → Diagnostic synthesis agent → Treatment recommendation agent → Physician review. The blackboard pattern allows all specialists to contribute concurrently without blocking each other.

Financial Trading

Market data stream → Analysis agents → Signal generation → Risk assessment agent → Position sizing agent → Execution agent. Kafka's ability to process millions of events/second makes it suitable for real-time trading systems where millisecond latency matters.

Key Terms & Quick Reference

Term Definition
AI Agent An autonomous system that perceives its environment, reasons about goals, selects actions, and executes them — repeatedly until the goal is achieved
Multi-Agent System (MAS) Multiple AI agents collaborating (or competing) to solve problems too complex for a single agent
Agentic AI The third phase of AI — autonomous systems that plan, reason, act, and self-correct without step-by-step human guidance
Event-Driven Architecture (EDA) A design paradigm where components communicate via immutable events through a broker, rather than direct API calls
Event An immutable record that something happened — includes event_type, timestamp, source, payload, and correlation_id
Event Stream A persistent, ordered, append-only log of events. Unlike queues, streams retain events enabling replay and audit
Event Bus / Broker Infrastructure routing events from producers to consumers — Kafka, RabbitMQ, AWS EventBridge, Redis Streams
Producer A component that publishes events. Decoupled from consumers — doesn't know or care who reacts to its events
Consumer A component that subscribes to and processes events. Multiple consumers can independently react to the same event
Topic A named category of events (Kafka). Producers write to topics; consumers subscribe to topics
Partition A topic is split into N ordered partitions. Multiple consumers process different partitions in parallel for scale
Offset Consumer's position in a partition. On restart, consumer resumes from last committed offset — no events lost
Consumer Group N instances of the same consumer collectively consuming a topic. Kafka distributes partitions evenly for load balancing
Exactly-Once Semantics Guarantee that each event is processed exactly once, even across failures — critical for financial/medical agents
Event Sourcing Storing all state changes as events — enables full replay, time-travel debugging, and complete audit trail
CQRS Command Query Responsibility Segregation — separate event streams for write (commands) and read (queries) paths
Orchestrator A controlling agent that decomposes goals into tasks and assigns them to worker agents via events
Worker Agent A specialist agent that executes a specific type of task assigned by an orchestrator or marketplace
Blackboard Pattern All agents share a common event stream — any agent can publish or consume, enabling emergent collaborative solutions
Market-Based Pattern Tasks posted as events; agents bid; allocator assigns to best bidder — self-organizing load balancing
ReAct Reason + Act — agent alternates between thinking about what to do (Thought) and doing it (Action), observing results at each step
Tool Calling LLM's ability to invoke external functions (web search, code execution, APIs) during the agent loop
Correlation ID A unique identifier linking all events belonging to one goal — enables end-to-end tracing across multiple agents
Vector Database Storage system for embeddings — enables semantic search for long-term agent memory. Examples: Pinecone, Chroma, Weaviate
Apache Kafka Distributed event streaming platform by Confluent — industry standard for high-throughput, fault-tolerant event streaming
Predictive AI Phase 1 — AI trained on historical data to classify or predict. Reactive and narrowly scoped (e.g., fraud detection)
Generative AI Phase 2 — AI that creates new content (text, images, code) from learned distributions. Examples: GPT-4, DALL·E
